# Интеграция GUI с расчётным ядром 2.1

Дата: 20 октября 2026 года

Статус: проект спецификации первого этапа интеграции

Основание: утверждённая архитектура `2026-10-20-craneplan-3-0-calculation-core-design.md` и реализованное ядро 2.1

## 1. Цель

Подключить расчётное ядро 2.1 к существующему настольному интерфейсу без преждевременной замены алгоритма поиска координат. Пользователь должен сохранить привычный расчёт до трёх вариантов, но получить независимую проверку каждого варианта, числовое объяснение результата и воспроизводимый JSON-протокол.

Первый этап считается завершённым, когда вариант, найденный текущим оптимизатором для одного крана Liebherr 130 EC-B 6, преобразуется в схему версии 3, проверяется ядром 2.1 и получает в GUI понятный статус. Неподтверждённый вариант можно изучить, но нельзя выпустить в составе предварительного ППРк.

## 2. Границы этапа

В этап входит:

- адаптация текущего `ProjectInput` к `ProjectV3`;
- адаптация однокранового `ScenarioResult` к `ProjectSolutionV3`;
- независимый запуск `run_engine_v21` после старого `optimize`;
- явное подтверждение пользователем фактических масс и оснастки;
- русские статусы и причины проверки в интерфейсе;
- блокировка выпуска ППРк для неподтверждённого варианта;
- сохранение JSON-протокола рядом с проектом;
- автоматические тесты адаптера, политики выпуска и сквозного расчётного сервиса.

В этап не входит:

- перенос поиска координат в ядро 2.1;
- проверка двух кранов новым ядром;
- расчёт пристёжек новым ядром;
- моделирование всех перегрузок между несколькими складами;
- расширение паспортного каталога V3 за пределы уже подтверждённой конфигурации `LIEBHERR-130-ECB-6-60-V3`;
- изменение формата старых сохранённых проектов.

## 3. Выбранный подход

Применяется схема «поиск старым алгоритмом, независимая проверка новым ядром»:

```text
GUI ProjectInput
      ↓
старый optimize() → до 3 ScenarioResult
      ↓
адаптер ProjectInput/ScenarioResult → ProjectV3/ProjectSolutionV3
      ↓
run_engine_v21()
      ↓
IntegrationVerification
      ↓
GUI: статус, измерения, причины, возможность выпуска
      ↓
project.json + calculation_protocol_v21.json + предварительный ППРк
```

Старый оптимизатор временно остаётся единственным генератором координат. Его статус `PASS` не считается подтверждением безопасности. Решение для выпуска определяется только результатом независимой проверки и политикой интеграции.

## 4. Компоненты

### 4.1 `engine/gui_adapter.py`

Новый модуль не зависит от Tkinter. Он:

- создаёт один этап `MAIN_STAGE` для текущего проекта;
- переносит границу площадки, контур здания, запретные зоны и расстояния установки;
- формирует операции для точек подачи;
- сопоставляет старый идентификатор крана с конфигурацией V3;
- преобразует координаты однокранового варианта в `ProjectSolutionV3`;
- возвращает структурированные проблемы адаптации вместо исключений интерфейса.

### 4.2 `engine/integration.py`

Сервис интеграции получает текущий проект, старый сценарий и каталог V3. Он запускает адаптер, затем `run_engine_v21`, переводит результат в прикладной статус и формирует русские сообщения.

Сервис не импортирует Tkinter и пригоден для модульных и сквозных тестов.

### 4.3 Изменения GUI

`CranePlanApp.run_calculation` сохраняет существующий поиск вариантов, затем вызывает сервис интеграции для каждого варианта. В выводе варианта появляется отдельный блок «Независимая проверка ядром 2.1».

На вкладке грузов добавляется флаг «Массы грузов и оснастки сверены с проектными документами». Флаг по умолчанию снят, сохраняется в проекте и автоматически снимается после изменения таблицы грузов. Без подтверждения расчёт и просмотр вариантов разрешены, но итоговый статус не может быть выше `EXPERT_REVIEW_REQUIRED`.

После расчёта пользователь выбирает один вариант в поле «Вариант для выпуска». По умолчанию выбирается первый вариант со статусом `VERIFIED` или `VERIFIED_WITH_CONDITIONS`; если таких нет, выбирается первый вариант только для просмотра. Сравнение всех вариантов остаётся на вкладке расчёта, а итоговый ППРк строится только для выбранного варианта.

`CranePlanApp.save_and_report` проверяет политику выпуска. Отсутствие подтверждённого варианта блокирует PDF и перечисляет конкретные причины. Просмотр расчёта и предварительных схем остаётся доступным.

### 4.4 Сохранение протокола

При сохранении проекта индекс выбранного варианта и результаты независимой проверки всех вариантов добавляются в `project.json`. Протокол выбранного подтверждённого варианта записывается в:

`reports/calculation_protocol_v21.json`

Файл содержит версию алгоритма, хеш входных данных, хеш результата, источники, измеренные значения и причины отклонения.

## 5. Преобразование исходных данных

### 5.1 Источники и доказательность

- Геометрия, точки подачи и отметки получают источник `PROJECT` с указанием элемента текущего проекта.
- Типовые массы до подтверждения пользователем сохраняют явный источник `ASSUMPTION` из библиотеки грузов.
- После установки флага подтверждения массы получают дополнительный источник `PROJECT` с записью о пользовательской сверке. Наличие исходного библиотечного допущения само по себе не должно оставлять результат в экспертном статусе: адаптер формирует итоговый `LoadSpec` с проектным источником подтверждения и сохраняет происхождение значения отдельным сообщением протокола.
- Паспортные данные крана поступают только из каталога V3.
- Адаптер не создаёт фиктивные нормативные или паспортные ссылки.

### 5.2 Этап и высоты

На первом этапе создаётся один этап `MAIN_STAGE`. Его монтажный горизонт равен максимальной отметке точки подачи. Отметка назначения операции берётся из `WorkPoint.level_m`.

Проверка высоты ядра 2.1 применяется только к свободностоящей конфигурации. Если старый вариант использует пристёжки или принятую высоту выше свободностоящей, интеграционный статус становится `EXPERT_REVIEW_REQUIRED`, поскольку ядро 2.1 ещё не проверяет паспортную схему пристёжек.

### 5.3 Операции и неполное назначение грузов

Для каждой точки подачи создаётся операция назначенного ей активного груза. Активный груз без собственной точки подачи проверяется на всех существующих точках, как в текущем консервативном поведении программы. Пользователь не обязан наносить отдельную точку для каждого груза.

Количество подъёмов берётся из `Load.lifts`. Масса, оснастка и габариты берутся из отредактированной таблицы грузов. Высота строповки первого этапа равна редактируемому предположению 1,5 м, явно отмеченному как `ASSUMPTION`.

### 5.4 Источник перемещения груза

Для полной проверки операции нужен однозначный источник:

- если задана ровно одна зона складирования, используется её центроид;
- если зон складирования нет и задана зона разгрузки, используется её центроид;
- если задано несколько зон складирования либо отсутствуют все логистические зоны, адаптер возвращает `LOGISTICS_SOURCE_AMBIGUOUS` или `LOGISTICS_SOURCE_REQUIRED`.

В этих случаях старый вариант остаётся видимым, но получает статус `EXPERT_REVIEW_REQUIRED` и не допускается к выпуску. Выбор ближайшей зоны скрыто не выполняется.

### 5.5 Сопоставление крана

На первом этапе поддерживается только базовая паспортная запись:

`LIEBHERR-130-ECB-6-60` → `LIEBHERR-130-ECB-6-60-V3`

Если старый оптимизатор принял укороченную стрелу из разрешённого ряда, адаптер создаёт производную конфигурацию для фактической длины. Вылет ограничивается этой длиной, а грузоподъёмность берётся по полной 60-метровой характеристике как консервативная нижняя оценка. Производная конфигурация получает стабильный идентификатор, исходную паспортную ссылку и явную запись метода в протоколе. Такой вариант получает `VERIFIED_WITH_CONDITIONS`, пока для соответствующей длины не внесена отдельная паспортная характеристика.

Другой кран не считается ошибочно проверенным. Он получает причину `CONFIGURATION_NOT_IN_V3_CATALOG` и статус `EXPERT_REVIEW_REQUIRED`.

## 6. Статусы интеграции

GUI использует четыре русских статуса:

- `VERIFIED` — ядро вернуло `VALID`, адаптация полная;
- `VERIFIED_WITH_CONDITIONS` — ядро вернуло `VALID_WITH_CONDITIONS`, условия перечислены;
- `EXPERT_REVIEW_REQUIRED` — исходные данные нельзя однозначно преобразовать либо ядро 2.1 ещё не охватывает конфигурацию;
- `REJECTED` — ядро вернуло `INVALID` или обязательное ограничение не выполнено.

Политика выпуска:

| Статус | Просмотр | Предпросмотр листов | Выпуск ППРк |
|---|---:|---:|---:|
| `VERIFIED` | да | да | да |
| `VERIFIED_WITH_CONDITIONS` | да | да | да, с печатью условий |
| `EXPERT_REVIEW_REQUIRED` | да | да, с водяным знаком | нет |
| `REJECTED` | да | да, с отметкой об отказе | нет |

## 7. Представление результатов

Для каждого варианта интерфейс показывает:

- итоговый статус;
- проверенную конфигурацию;
- критическую операцию по грузоподъёмности;
- максимальный вылет;
- доступную грузоподъёмность и запас в килограммах;
- требуемую высоту крюка и запас по высоте;
- коды причин и их русские пояснения;
- хеш входных данных и идентификатор протокола после сохранения.

Коды ядра не выводятся пользователю без перевода. Технический код сохраняется рядом с русским сообщением в JSON-протоколе.

## 8. Ошибки и отказоустойчивость

- Ошибка адаптации одного варианта не уничтожает остальные варианты.
- Исключение ядра показывается как `EXPERT_REVIEW_REQUIRED`, записывается в диагностический результат и блокирует выпуск этого варианта.
- Старый `ScenarioResult` не изменяется и остаётся доступным для схемы и сравнения.
- Протокол пишется атомарно через временный файл и замену целевого файла после успешной сериализации.
- Отсутствующий каталог V3 блокирует подтверждение, но не закрывает приложение.
- Неподдерживаемая схема или неизвестный кран никогда не переводятся в `VERIFIED`.

## 9. Изменения моделей приложения

Добавляется отдельная неизменяемая модель результата интеграции, а не новые динамические поля в `ScenarioResult`:

```text
ScenarioVerificationV21
  scenario_index
  status
  release_allowed
  messages
  engine_result
  protocol
```

`CranePlanApp` хранит список проверок параллельно `self.scenarios`. Индексы обоих списков совпадают. Это позволяет позднее заменить генератор вариантов, не смешивая старую расчётную модель с новой.

Отдельное поле состояния хранит индекс варианта для выпуска. Пустое или вышедшее за диапазон значение блокирует выпуск с сообщением «Выберите рассчитанный вариант».

## 10. Тестирование

Обязательные тесты первого этапа:

1. Полный однокрановый вариант 130 EC-B 6 со стрелой 60 м и подтверждёнными массами преобразуется и получает `VERIFIED`.
2. Неподтверждённые типовые массы переводят геометрически допустимый вариант в `EXPERT_REVIEW_REQUIRED`.
3. Изменение груза автоматически снимает подтверждение масс.
4. Разрешённая укороченная стрела получает производную конфигурацию и `VERIFIED_WITH_CONDITIONS`.
5. Недостаточная грузоподъёмность возвращает `REJECTED` с измеренным значением и пределом.
6. Недостаточная свободностоящая высота возвращает `REJECTED`.
7. Вариант с пристёжками получает `EXPERT_REVIEW_REQUIRED`, пока пристёжки не проверяются ядром.
8. Кран без записи V3 получает `CONFIGURATION_NOT_IN_V3_CATALOG`.
9. Несколько складских зон без назначения дают `LOGISTICS_SOURCE_AMBIGUOUS`.
10. Активный груз без отдельной точки проверяется на всех точках подачи.
11. Неподтверждённый вариант доступен для просмотра, но блокирует выпуск.
12. Подтверждённый вариант разрешает выпуск и сохраняет валидный JSON-протокол.
13. Итоговый отчёт получает только выбранный вариант; сравнительный вывод GUI сохраняет все варианты.
14. Ошибка одного варианта не препятствует проверке остальных.
15. Повторный запуск одинакового проекта даёт одинаковые хеши содержательной части протокола.
16. Полный существующий набор тестов остаётся зелёным.

## 11. Критерии завершения

- GUI после обычного расчёта показывает независимый статус каждого варианта.
- Выпуск ППРк нельзя выполнить для непроверенного или отклонённого варианта.
- Для подтверждённого однокранового варианта 130 EC-B 6 сохраняется протокол ядра 2.1.
- Ни один неподдерживаемый кран или неоднозначное логистическое допущение не маскируется как безопасное решение.
- Существующие функции плана, разреза, обрезки PDF, пристёжек, двух кранов и формирования схем продолжают работать в прежнем режиме просмотра.
- Автоматические тесты доказывают поведение адаптера, политики выпуска и интеграционного сервиса.

## 12. Следующий этап

3. перенести генерацию координат и ранжирование в ядро версии 2.2;
