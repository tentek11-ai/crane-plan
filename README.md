# КранПлан

Исследовательский проект по автоматизации проектирования размещения башенных кранов на строительной площадке.

## Текущий этап

- Версия интерфейса, расчётного ядра и переносимой сборки: `3.0.2`.
- Этап: работоспособная автономная версия для Windows с высотно-зависимыми опасными зонами, поиском маршрутов, графической СОЗР и проверкой одного или двух кранов.
- Реализован полный комплект ППРк: первые четыре служебные страницы, 22 условных раздела записки, расчётные листы A3/A2/A1, неизменённые проверенные типовые клипы и объединение внешних PDF с сохранением формата и поворота. Состав и ссылки рассчитываются по фактическим страницам.
- Разделы «Каталог кранов» и «Нормативные документы» используют автономную локальную библиотеку. Краны можно добавлять вручную; пользовательские характеристики участвуют в подборе только с обязательной экспертной проверкой.
- Переносимая сборка формируется в `10_exports/releases/CranePlan_Portable_3.0.2`.

## Опасные зоны, маршруты и СОЗР

Каждая зона имеет имя, высоту от отметки `0`, горизонтальный запас и один из трёх типов:

- `FULL_EXCLUSION` — полный запрет для башни, стрелы и груза;
- `LOAD_PROHIBITED` — груз не проносится, пустая стрела допускается только по высотной проверке;
- `HEIGHT_OBSTACLE` — груз и стрела могут пройти выше зоны с запасом по умолчанию 3 м.

Маршрут строится в полярном графе по углу, вылету и высоте. По умолчанию шаг угла равен 1°, шаг вылета — 0,5 м. Каждое принятое ребро затем проверяется точными геометрическими предикатами. Выбирается маршрут с максимальным минимальным запасом, затем кратчайший.

Нормативная огибающая груза должна целиком оставаться внутри площадки на всех радиальных участках и дугах. Для двух кранов непрерывно проверяются проход стрелы около второй башни, взаимное пересечение стрел и сближение груза со стрелой второго крана. Голубая область СОЗР строится консервативно; полный технический вылет показывается отдельно пунктирной окружностью.

СОЗР в версии 3.0 — расчётно-графическая схема, а не готовый файл настройки прибора. Координаты и секторы переносит, налаживает и проверяет ответственный специалист по паспорту фактического крана.

Проекты прежних схем мигрируются в схему 4 с конфигурацией выпуска ППРк без перезаписи исходного `project.json` до явного сохранения. Старые полигоны помечаются как непроверенные `FULL_EXCLUSION` и требуют экспертного уточнения.

## Выпуск полного ППРк

Комплект объединяет расчётную часть выбранного варианта/протокола, типовые условные тексты и проверенные клипы, внешние специальные проекты и подтверждения. Бадья, длинномерный груз, площадки, проёмы и совместная работа включают соответствующие разделы; исходный PDF проекта-аналога не нужен. Внешний проект регистрируется и прикладывается, но не считается рассчитанным программой.

Пять статусов: предварительный расчёт, на проверку, на согласование, утверждён, в производство. В редакторе показаны запрошенный и эффективный статусы; сохранение недоступного статуса блокируется. Для черновика явно выберите предварительный статус. Экспертный вариант с пристёжками и действительным протоколом без критических отказов можно сохранить только как `PRELIMINARY`, с предварительным титулом и предупреждением «НЕ ДЛЯ ВЫПУСКА». Отклонённый расчёт, критический отказ, отсутствие протокола, устаревшие данные или протокол другого варианта блокируют и предварительное сохранение. Окончательный выпуск требует актуального протокола именно выбранного варианта, закрытых замечаний, подтверждённых грузов, восьми заполненных строк согласований и проверенных обязательных внешних документов. Программа не создаёт подписи и не утверждает проект автоматически. Пристёжки сохраняют требование экспертной проверки.

После изменения инженерных данных выполните повторный расчёт. Изменение реквизитов, приложения или его байтов делает предпросмотр устаревшим; сохранение заново собирает комплект и проверяет текущие данные. Заменённый внешний PDF требует повторного подтверждения ревизии. Нечитаемый клип заменяется владельцем библиотеки после ручной проверки и обновления SHA-256/статуса в манифесте; восстановление доверенной библиотеки предпочтительно автоматической обработке изображения.

Переносимая сборка работает без сети при наличии всех папок приложения и runtime. Локальные брошюры ожидаются в `app/library/cranes/brochures`, нормативные документы — в `app/library/regulations/documents`, их реестры — в соседних `manifest.json`. Клипы и тексты включены в `app/05_src/crane_plan/assets/pprk`. Полный порядок работы и условия пяти статусов приведены в [руководстве пользователя](07_docs/USER_GUIDE.md).

Сгенерированный комплект требует проверки и утверждения ответственным специалистом. Расчёт фундамента, конструктивных узлов пристёжек, передачи усилий, монтажа/демонтажа и защитного экрана выполняется вне CranePlan.

Ограничение метода: дискретная сетка не доказывает глобальную оптимальность, а консервативное сжатие кандидатов может отбросить редкую внутреннюю позицию. Поэтому отсутствие варианта не заменяет инженерный анализ.

## Куда положить первые материалы

- Основные научные статьи: `01_sources/01_core_articles/`
- Оригиналы ППРк: `01_sources/03_pprk/01_original/`

Оригинальные исходные файлы не изменяются и не перезаписываются. Из-за размера и возможной чувствительности они не включаются в Git; целостность ключевых файлов фиксируется контрольными суммами SHA-256 в реестрах.

## Принципы проекта

- Распознавание, инженерный расчет и подбор реального оборудования разделяются.
- Расчеты в реальных единицах выполняются только после калибровки масштаба.
- Неизвестные данные отмечаются как `UNKNOWN` или `REQUIRED INPUT`.
- Все инженерные результаты требуют проверки специалистом.
- Значимые эксперименты должны быть воспроизводимыми.
- Validation-ППРк не используются для настройки метода до независимой проверки.

Для статусов `COORDINATION`, `APPROVED` и `PRODUCTION` обязательны проверенные PDF с ID `crane_passport`, `foundation_project` и `erection_project`; при пристёжках нужен `tie_in_project`, при компенсации опасной зоны экраном — `protective_screen_project` и типовой лист экрана. Флажок «обязательный» не отменяет эти требования. Заменённые байты требуют повторной проверки SHA-256.

В карточке выпуска укажите точную дату `ГГГГ-ММ-ДД`. Нормативные документы вместе с редакцией, статусом, сроками и источником публикуются в записке. Истёкший или непроверенный норматив блокирует повышенный статус; текущий реестр содержит незакрытые статусы, которые программа не подтверждает автоматически. В редакторе груза заполните тип оснастки, число ветвей, марку/номер стропа, допустимую массу и подтверждающий документ, затем явно подтвердите проверку. Старые проекты получают пустые неподтверждённые значения.

Все расчётные страницы показывают выбранный вариант и протокол; штампы используют реквизиты карточки выпуска. Состав пагинируется и при отсутствии внешних PDF. Непечатаемые заголовки и таблицы выявляются при подготовке. Запрещённые реквизиты исходного шаблона проверяются во входах и физическом PDF до замены предыдущего результата. Сквозной проверочный образец занимает 50 страниц.

## Запуск исходной версии

В выпуске используется точная дата: она печатается на титуле и определяет его год; противоречащий год блокирует повышенный статус. Проверяющий и утверждающий назначаются явными ролями в восьми строках согласований. Руководитель автоматически не получает эти роли. Проверяются исходные векторные подложки и декодированный XMP до растеризации/публикации; для растровых надписей без текстового слоя сохраняется необходимость визуальной проверки.

Нормативный CSV использует единую девятиколоночную схему с раздельными `verification_status` и `software_status`. Неоднозначные строки не принимаются; статус реализации не считается проверкой источника. Полные заголовки внешних страниц с ID документа измеряются до допуска к сохранению.

PDF-подложки рисуются из временных копий тех же байтов, которые прошли проверку; замена исходного пути во время сборки не подменяет изображение. Сохранение из GUI дополнительно отклоняет изменившийся исходник. Метаданные проверяются рекурсивно, включая вложенные Form XObject и циклические ресурсы. DTD, объявления сущностей и некорректный XML блокируют любой статус выпуска, включая предварительный, независимо от флагов приложения.

Отсутствующая при захвате подложка фиксируется недоступной в копии для рендера: позднее появление файла не добавляет непроверенный фон. XML декодируется с учётом BOM, порядка байтов и объявленной кодировки; DTD/ENTITY запрещаются до входа в парсер, включая UTF-16/32 без BOM. Заполнители оснастки распознаются и после подписей полей, например «Номер: НЕ ЗАПОЛНЕНО».

Проверка оснастки учитывает поле и смысл отрицания. Ссылки на «отсутствующую схему» или «непроверенную ведомость» остаются неподтверждёнными во всех падежных формах. Записи «Дефектов нет», «нет замечаний» или «отсутствуют дефекты» допустимы рядом с фактическими сведениями о типе, стропе и документе; сами по себе такие замечания не заменяют идентификацию. Значения «Паспорт: нет», «Строп — нет» и «схемы нет» блокируют повышенный статус.

Каждое поле оснастки требует своих сведений: конкретного типа («Канатный», «Траверса»), марки/номера стропа (`4СК-5,0`, `Строп 4СК-5,0 №123`, `Марка: TR-ABC`) и названного документа с номером, датой или кодом («Паспорт №123», «Акт от 03.11.2026», «Протокол №TEST-ABC»). Общее описание осмотра не заменяет эти реквизиты. Номер между названием и отрицанием («Паспорта №123 нет») не снимает блокировку; отдельная положительная запись «Паспорт №123. Дефектов нет» допустима. Десятичная запятая в марке сохраняется.

Реквизит должен быть явно связан с заголовком документа: номер/код после `№`, «номер», `N`, `ID`, «шифр», «рег. номер»; дата — после «от» или «дата». Количество дефектов, замечаний, страниц, масса и грузоподъёмность не становятся номером документа. «Паспорт: дефектов 0» и «Акт проверки (замечаний 0)» остаются неподтверждёнными. Узкий старый формат «Испытательный паспорт 123» сохраняется; неоднозначные записи программа не дополняет выдуманными реквизитами.

Явный номер допускает обычное название с прилагательными и союзами: «Акт проверки и испытаний №42», «Паспорт четырёхветвевого стропа №123». Название и реквизит должны оставаться в одной фразе. Дата проверяется целиком: `2026-11-03-99` и `03.11.2026.99` не подтверждают документ; `29.02.2024` допустима, `29.02.2023` — нет. Обычная точка в конце предложения допустима.

Номер должен принадлежать самому документу. «Паспорт находится на странице №42», «Акт ссылается на испытание №17» и ссылки на листы или заявки не подтверждают документ. Используйте именное название, например «Протокол испытаний: №42»; незнакомое развёрнутое название можно сократить до «Акт №42». Двоеточие перед номером допустимо, переход через тире или границу предложения — нет.

Дата также должна принадлежать самому документу. «Паспорт содержит ссылку на акт от 03.11.2026» и «Акт приложен к паспорту от 2024-02-29» остаются неподтверждёнными. Прямые записи «Акт от 03.11.2026», «Паспорт стропа от 03.11.2026» и «По акту приёма-передачи оснастки №42» сохраняются.

Двоеточие или тире отделяет комментарий после уже идентифицированного типа, стропа или документа. Одно число в описании не устанавливает идентичность: «Паспорт содержит 1 ссылку: акт от 03.11.2026» остаётся неподтверждённым. Прямые реквизиты «Паспорт №1: дефектов нет» и «Акт №1 — рисков нет» допустимы.

Проверка XML охватывает также развёрнутые имена тегов и атрибутов, URI пространств имён и неиспользуемые объявления `xmlns`, включая числовые сущности в URI. Безопасные пространства имён сохраняются при включении внешнего PDF.

## Расчётное ядро 2.1

Точка входа для разработчика — `crane_plan.engine.run_engine_v21`. Запрос содержит модель проекта схемы 3, прослеживаемый каталог, явно заданные координаты кандидатов и, при наличии, предлагаемое решение. Сервис:

- детерминированно проверяет каждую операцию по вылету, грузоподъёмности, высоте, маршруту, опасной зоне и положению основания;
- между паспортными вылетами принимает грузоподъёмность следующей большей точки таблицы без линейной интерполяции;
- независимо перепроверяет предложенное решение, не используя результат первичного оценщика;
- выдаёт измеренные значения, пределы и стабильные коды причин;
- создаёт канонический протокол JSON с версиями, источниками и SHA-256 входа и результата.

Минимальный импорт:

```python
from crane_plan.engine import EngineRequestV21, run_engine_v21

result = run_engine_v21(EngineRequestV21(
    project=project_v3,
    catalog=crane_configurations_v3,
    candidate_coordinates=((x_m, y_m),),
    proposed_solution=solution_v3,
    run_id="calculation-001",
    created_at="2026-10-20T10:00:00+03:00",
))
```

## Проверка и выпуск варианта в интерфейсе

Рабочая последовательность: текущий оптимизатор находит до трёх вариантов → ядро 2.1 независимо проверяет каждый вариант → пользователь выбирает один вариант → программа разрешает или блокирует выпуск предварительного ППРк.

Статусы независимой проверки:

- `VERIFIED` — вариант проверен и может быть выпущен;
- `VERIFIED_WITH_CONDITIONS` — выпуск разрешён, условия печатаются в отчёте;
- `EXPERT_REVIEW_REQUIRED` — предварительный просмотр содержит отметку «Не для выпуска»; повышение статуса блокируется;
- `REJECTED` — вариант не выполнил обязательное ограничение; повышение статуса блокируется.

Перед подтверждением варианта пользователь должен отметить, что массы грузов, оснастка и принятое значение высоты строповки сверены с проектными документами. Изменение или удаление груза автоматически снимает подтверждение и очищает устаревшие результаты.

Для выпущенного варианта рядом с PDF сохраняется `reports/calculation_protocol_v21.json` с источниками, измеренными значениями, кодами причин и SHA-256 входа/результата.

Ограничения: оптимизатор перебирает координаты по дискретной сетке, а независимое ядро пока подтверждает паспортные конфигурации `Liebherr 130 EC-B 6`. Пристёжки, фундамент, монтаж/демонтаж, полевая наладка координатной защиты и краны без прослеживаемой записи V3 требуют отдельной инженерной проверки.

Проверка 20.10.2026 на Python 3.12.14:

```powershell
$env:PYTHONPATH=(Resolve-Path '.\05_src').Path
python -m unittest discover -s 06_tests -p "test_engine_*.py" -v
python -m unittest discover -s 06_tests -v
```

Автоматические тесты GUI проверяют оркестрацию без запуска `mainloop`; переносимая Windows-сборка требует отдельной ручной приёмки перед публикацией.
